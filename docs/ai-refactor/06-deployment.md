# Staging deployment and rollback

This workspace has not deployed a revision or called Gemini live. The current app defaults to `GEMINI_ENABLED=false`; the local configuration diagnostic reported an enabled development setup with key present, but that does not describe Cloud Run. `.env.example` contains a model override distinct from the `config.py` default. Keep the intended model unchanged until checked with the actual staging key.

1. Build from this branch's reviewed commit, recording Cloud Build FETCHSOURCE commit, image digest and Cloud Run revision. Compare all three before traffic moves. Keep the previous deployable revision.
2. Before moving traffic, run `alembic upgrade head` from `backend/` as a migration job against the target database. It must apply revision `c4d5e6f70819`, creating `hr_ai_role_scope_policies`; chat, suggestions and report analysis return 503 without this table even when Gemini is disabled. Inspect only nonsecret environment values and Secret Manager **references** on the staging revision: `GEMINI_ENABLED`, model name, API key reference, database URL references, network egress and VPC. Never print secret values. Enable Gemini on staging only with an approved usage budget.
3. In the deployed environment, run `python -B -m app.ai.providers.diagnose` for safe metadata, then `python -B -m app.ai.providers.diagnose --live` when billable live testing is authorized. Require SUCCESS for model access, minimal text and structured JSON. A valid API request without generated content is a failure.
4. On a dedicated PostgreSQL test database, inspect role codes and assignment counts read-only before deciding any alias: `SELECT r.role_code, count(a.user_role_assignment_id) FROM hr_roles r LEFT JOIN hr_user_role_assignments a ON a.role_id = r.role_id GROUP BY r.role_code ORDER BY r.role_code;`. Do not equate `USER` with `EMPLOYEE` without confirming its business meaning.
5. Verify multiple-role ADMIN, MANAGER direct-report limits, EMPLOYEE self-only behavior, payroll and report-run ownership, cross-user draft IDs, stale/expired revisions, and published/effective/answerable knowledge sections with real SQL. Use sanitized accounts and documents; inspect logs for provider outcome categories and suggestion availability reasons without logging document content.
6. Exercise the browser flow: leave request → compound date → remaining fields → form review, plus a leave-balance interruption and a provider timeout retry. Confirm draft ID/revision survives recoverable errors. Check HR and AI endpoints agree on the same actor and requested scope.

Verify the required scope migration has completed on the target database before moving traffic. An empty policy table uses defaults; existing deployments do not need demo data reseeded. Do not run seed scripts or destructive tests against production. If staging fails, route traffic back to the retained revision and restore the previous Gemini enable/model configuration; do not change role mappings or substitute models to mask a failure. `docs/GCP_DEPLOY.md` contains the existing Cloud Run build context and general runtime setup.
